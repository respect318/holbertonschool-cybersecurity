# 6-chain.md: The Chain and Its Signature - Post-Compromise Analysis

This post-compromise report documents the technical analysis of two distinct privilege escalation chains successfully executed within the host environment. The purpose of this note for Meridian's engineering team is to detail how the isolated primitives in both paths were combined into complete compositions, why neither half of either chain was sufficient on its own, and how to build robust, mechanism-keyed detection rules that transfer beyond this specific host.

---

## Part 1: The First Path - Sudo Misconfiguration and Insecure Parameter Expansion

The first privilege escalation path was constructed by combining two distinct vulnerability primitives. The first primitive was a `sudo` misconfiguration that allowed a standard, unprivileged user to execute a specific system maintenance script without requiring a password. The second primitive was an insecure wildcard (`*`) parameter expansion located inside that maintenance script, specifically passed to the `tar` utility as an argument. 

The composition of these primitives worked in a precise order. First, the attacker created specifically named dummy files (such as `--checkpoint=1` and `--checkpoint-action=exec=sh`) inside a working directory where they had write access. Next, the attacker executed the maintenance script using `sudo`. When the script executed the `tar *` command in that directory, the shell expanded the wildcard into the names of the malicious files, passing them as active parameters to `tar`. This causal connection forced `tar` to execute an interactive shell, inheriting the elevated privileges granted by the `sudo` execution.

Neither primitive in this first path was sufficient to achieve privilege escalation alone. The `sudo` misconfiguration, considered on its own, was entirely insufficient because it strictly limited execution to a single, predefined script; it did not grant arbitrary command execution or an interactive root shell. Conversely, the insecure wildcard parameter expansion in `tar`, considered on its own, was insufficient because triggering it without the `sudo` rule would only execute the resulting shell with the limited privileges of the current unprivileged user. Only the causal combination of the two—where the execution vulnerability is triggered inside the elevated context—resulted in a full system compromise.

The audit records produced by my actions for this path consist of `EXECVE` and `SYSCALL` events. The logs capture the initial `sudo` execution, followed by the script invoking `tar`, and finally, an `EXECVE` record showing the `tar` process spawning `/bin/sh` with an Effective UID (EUID) of 0. An actionable detection rule must not rely on the specific script name or user. Instead, the detection logic transfers to the next host by keying on the underlying mechanism. A robust rule would monitor the process tree for any standard data manipulation utility (like `tar`, `find`, or `awk`) acting as a parent process that unexpectedly spawns an interactive shell (such as `sh` or `bash`) as a child process with an EUID of 0.

## Part 2: The Second Path - Capability Exposure and SUID PATH Hijacking

The second path required an entirely different methodology, built upon the composition of two distinct system primitives. The first primitive was a custom utility endowed with the `cap_dac_read_search` Linux capability, which bypasses file read permission checks across the system. The second primitive was an SUID-privileged binary that insecurely executed a helper command using a relative path rather than an absolute, hardcoded path.

The order and causal connection that made this combination work began with information gathering. First, the `cap_dac_read_search` capability was leveraged to read a protected root configuration file, revealing the exact, randomized name of the helper script the SUID binary was trying to call. Armed with this intelligence, the attacker crafted a malicious payload matching that exact filename in the `/tmp` directory and manipulated the `PATH` environment variable to prioritize `/tmp`. When the SUID binary was subsequently executed, it inherited the poisoned `PATH` environment and blindly executed the malicious payload with root privileges.

Neither primitive in this second path was sufficient on its own. The `cap_dac_read_search` capability, considered on its own, was insufficient because it only grants arbitrary file read access; it provides absolutely no execution context, memory manipulation, or file write access required to alter the system state. On the other hand, the SUID binary calling a relative path was entirely secure in isolation because the specific name of the helper command was obscured within a root-owned configuration file. Without the capability to read that file, an attacker could not blindly guess the filename to perform a PATH hijack. The capability mapped the vulnerability, enabling the exploitation of the execution flow.

The audit signature for this path spans `PATH`, `EXECVE`, and `SYSCALL` records. The logs capture the execution of the SUID binary by an unprivileged user (Real UID > 0), followed immediately by the binary spawning a child process whose executable resides in a temporary directory. To ensure the detection logic transfers beyond this attempt, the rule must not look for the specific SUID binary name or the randomized helper name. Instead, the detection must key on the privilege mechanism. An actionable rule would trigger an alert whenever an `EXECVE` syscall reveals a process transitioning to an EUID of 0 while the Real UID remains unprivileged, combined with the executed payload's absolute path originating from a world-writable directory (such as `/tmp/`, `/var/tmp/`, or `/dev/shm/`). This catches the core mechanism of unauthorized SUID hijacking regardless of the tools used.
