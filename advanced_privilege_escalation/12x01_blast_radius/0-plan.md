The primary and single objective of this engagement is to determine whether an attacker with developer access can sign and ship an Ardent release, and to establish the full reach of a build infrastructure compromise. I have a strict four-day window, which is approximately thirty hours, to achieve this goal and answer the client's question.

To serve this objective logically rather than just starting with what is convenient, I have allocated the four-day window across the following specific phases:
Phase 1: Source and Pipeline Enumeration (Day 1, 8 hours). I must start here because the objective centers entirely on the build system. Understanding the pipeline definition within the repository is the necessary prerequisite for achieving command execution on the infrastructure that builds it.
Phase 2: Environment Characterization and Boundary Crossing (Day 2, 8 hours). Once execution on a runner is achieved, I will meticulously map the container's namespaces and plan an escape to the underlying host when a documented technique has been correctly mitigated.
Phase 3: Expanding Access and Proving the Objective (Day 3, 8 hours). I will locate the signing authority and determine the maximum extent of the compromise within the internal segment to definitively prove if I can sign a release.
Phase 4: Consolidation and Reporting (Day 4, 6 hours). This time is reserved to write down what I learned, ensure all timelines are accurate, and document any limitations properly.

My strict stopping rule sets a specific time limit: I will give any single technical lead a maximum of four hours before stopping. The observable evidence that will tell me a lead is not going anywhere is an explicit system response showing a blocked mitigation. For example, if I encounter an unresolvable compiler error when adapting a public exploit, or diagnostic output showing a definitively blocked system call, I will abandon that lead. This evidence proves the environment lacks the prerequisite condition. I will then document the blocked path as a limitation and pivot to a new approach.

Logging will begin immediately, starting before the first engagement action is taken. I will maintain a continuous operator log in a structured text format. Every entry will record the exact timestamp, the specific command run, the raw output received, the technical decision made based on that output, and the final results.
