## Executive Summary

A structured audit of the MedDefense Active Directory account inventory identified 19 findings
across 20 privileged accounts: 7 Critical, 8 High, 3 Medium, and 1 Low. The environment
contains three service accounts with standing Domain Admins membership, four dormant privileged
user accounts that have not authenticated in more than 90 days, three accounts belonging to
departed or transferred employees that retain domain group memberships, and multiple enabled
privileged accounts with no MFA enrollment. These findings represent concrete, exploitable
misconfigurations in the current environment, not theoretical future risks.

The most critical finding in this audit is `svc_epic_int` (IAM-013, IAM-014): a service account
with Domain Admins membership that has not been used in 1,156 days and has no identified current
business function. This account directly replicates the identity path that enabled the prior
Cobalt Strike lateral movement event. In that incident, an attacker extracted credentials from
memory on a compromised endpoint, discovered the `svc_epic_int` password, and used Domain Admin
privileges to move laterally across the environment for three hours before detection. The
password had not been changed in three years. Three additional service accounts (`svc_backup`,
`svc_helpdesk`) carry identical Domain Admins membership with no evidence of privilege review.

This audit changes MedDefense's posture in two ways. First, it produces a complete, reproducible
inventory of every privilege misconfiguration in the current environment, ordered by severity and
mapped to specific accounts, so that remediation can be tracked and verified rather than
estimated. Second, it establishes the baseline against which future audits will measure
improvement. The remediation roadmap in this report, if executed in full, eliminates every
standing Domain Admin service account, enforces MFA across all privileged users, and removes all
departed-employee accounts — the three control categories whose absence directly enabled the
prior incident.

## Audit Scope and Methodology

**In scope:** All 20 Active Directory accounts with any privileged group membership exported
by Robert Kim following the post-incident review. Source file: `accounts.csv`.

**Out of scope:** Standard user accounts with no privileged group membership; cloud IAM roles
(addressed in the separate cloud security assessment); application service accounts not
represented in the Active Directory export.

**Tooling:** Findings were generated by `audit_iam.py`, a Python script that applies six
named checks to every account in the inventory and writes severity-scored output to
`iam_findings.json`. The same logic is applied to every account, eliminating the
inconsistency of manual review. All findings are traceable to a specific account row in
`accounts.csv` and a specific check function in `audit_iam.py`.

**Severity assignment** follows the MedDefense severity model (`severity_model.md`):

- **Critical:** Direct domain takeover path, standing privileged persistence, or direct
  replication of the prior incident identity path.
- **High:** Strong attack path requiring one additional condition (e.g., dormant privileged
  account, privileged account without MFA).
- **Medium:** Meaningful exposure or detection weakness (disabled account retaining groups,
  service account with Server Admins, non-privileged user with repeated security failures).
- **Low:** Hygiene issue unlikely to independently enable a major incident.

**Check functions applied:**
- `check_service_account_overpriv` — Domain Admins = Critical; Server Admins = Medium
- `check_dormant_privileged` — user > 90 days dormant with DA/SA = High; service > 365 days = Critical
- `check_mfa_coverage` — enabled privileged user without MFA = High
- `check_departed_or_transferred` — keyword match in description; Critical if privileged, High otherwise
- `check_disabled_with_groups` — disabled account with non-empty groups = Medium
- `check_no_mfa_high_risk` — enabled user without MFA = Low; escalated to Medium if repeated failures noted

## Detailed Findings

### IAM-001: Dormant Privileged User — admin.legacy (187 days)

**Account:** admin.legacy
**Severity:** High
**Check:** check_dormant_privileged
**Evidence (accounts.csv):** account_type=user; enabled=TRUE; privileged_groups=Domain Admins;
last_login_days_ago=187; mfa_enrolled=FALSE; description="Created for EHR migration 2021;
migration complete"
**Risk:** An enabled Domain Admin account that has not been used in 187 days is a standing
credential available to any attacker who extracts it from memory, captures it via phishing, or
finds it in a legacy configuration file. The "migration complete" description indicates the
account's stated purpose no longer exists. An attacker using this account gains full domain
administrative capability with no time constraint, enabling creation of new accounts, access to
ePHI systems, and disabling of audit controls. This finding also overlaps with IAM-003.
**Remediation:**
1. Disable `admin.legacy` in Active Directory immediately.
2. Remove Domain Admins group membership.
3. Confirm with the EHR migration project owner that no integration depends on this account.
4. Review AD audit logs for any activity from `admin.legacy` in the past 90 days.
5. If no current function is confirmed within 30 days, delete the account.

**Owner:** Identity and Access Management team
**Target completion:** Immediate (disable within 24 hours; deletion review within 30 days)

### IAM-012: Service Account with Domain Admins — svc_backup

**Evidence (accounts.csv):** account_type=service; enabled=TRUE;
privileged_groups=Domain Admins; last_login_days_ago=1; mfa_enrolled=N/A;

**Risk:** A service account running nightly backup automation with Domain Admins membership
has a credential that never expires, cannot enroll MFA, and presents the same attack surface
as `svc_epic_int`. An attacker who extracts this credential — from the backup server's memory,
from a configuration file, or from a compromised automation pipeline — gains permanent Domain
Admin access. The description "DA granted per legacy config" confirms this is a privilege
accumulation artifact, not a deliberate security decision. Backup functions do not require

destination.
**Remediation:**

   automation.

3. Create a new, scoped service account or migrate to Vault-issued dynamic credentials with
   a role granting only the required read permissions on source systems and write permissions
   on the backup destination.
4. Test backup jobs with the reduced-privilege account before deleting the old configuration.
5. Document the privilege justification for the new account.

**Owner:** IT Infrastructure team; Security team sign-off required
**Target completion:** 30 days (Domain Admins removal: immediate)

**HIPAA 164.312(d) context:** The HIPAA Security Rule at 45 CFR 164.312(d) requires covered
entities to implement procedures to verify that a person seeking access to ePHI is the one
claimed. MFA is the primary technical control that satisfies this requirement for privileged
accounts with domain-wide access to ePHI systems. Three enabled Domain Admin accounts without
MFA — including two belonging to departed or departed-equivalent users — represent a direct
gap against this implementation specification. Following the remediation of IAM-003, IAM-006,
and IAM-019 (disable or de-privilege the accounts), the remaining MFA gap among legitimate
active privileged users is zero, provided the Conditional Access MFA enforcement policy is
implemented as specified in the remediation roadmap.

time-limited credential scoped to the specific database or API the service requires; when the
TTL expires, the credential is automatically revoked at the target system. There is no standing
password to extract.
