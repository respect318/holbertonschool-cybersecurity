## Reconnaissance Report, Vellum Press portal
For: Sofia Reyes and the engagement file

## 1. Engagement overview

This report covers the reconnaissance phase of the authorized engagement against the Vellum Press staff portal. The target was the internal staff-facing web application used by editorial and administrative personnel to manage submissions, user accounts, and internal content workflows. The scope held for this phase was limited strictly to the staff portal's web front end and its directly reachable API endpoints, as listed in the authorization letter; no infrastructure outside that host list, no social engineering, and no denial-of-service style testing were in scope. Any endpoint or subdomain discovered during crawling that fell outside the authorized host list was noted but deliberately not probed further.

Burp Suite was used as the interception proxy for the entire reconnaissance phase. The proxy listener was configured on localhost, and the embedded Chromium browser was pointed at it so that first-pass exploration could happen inside a controlled, already-trusted environment. An external browser was also configured to route through the same listener, with Burp's CA imported into that browser's trust store, so that authenticated staff-portal sessions established outside the embedded browser could still be observed and replayed. This dual-browser setup let normal, everyday navigation of the portal (login, dashboard, submission review, account settings) generate traffic that landed directly in Proxy > HTTP history for later analysis.

Target scope was configured early, using the "Add to scope" action from HTTP history once the staff portal's host and its API subdomain were confirmed, and the "Show only in-scope items" filter was kept on for the remainder of the engagement. This kept Burp's history, Repeater tabs, and Site map free of noise from third-party analytics, CDN assets, and advertising beacons that the portal's pages pulled in, and it enforced the authorization boundary at the tool level rather than relying purely on discipline. Site map was left to populate passively as pages were browsed rather than driven with an active, unauthenticated spider, since the engagement rules asked for organic discovery over aggressive crawling at this stage.

## 2. The man-in-the-middle and the certificate

Reading the contents of HTTPS traffic in Burp requires a deliberate, consented man-in-the-middle position, and it is worth being precise about why that works and what it depends on. When the browser opens a connection to the staff portal over HTTPS, Burp's proxy listener intercepts that connection before it reaches the real server. Burp does not simply "peek" at an existing TLS tunnel; TLS is designed so that this is not possible from a passive vantage point. Instead, Burp terminates the browser's TLS connection at the proxy itself, presenting the browser with a certificate for the requested host that is signed by Burp's own locally generated Certificate Authority rather than by the portal's real certificate authority.

Separately, Burp opens its own, independent TLS connection out to the real Vellum Press server, using standard TLS on that leg exactly as a normal browser would. From the server's perspective, Burp looks like an ordinary client. From the browser's perspective, Burp looks like the server. In between, the traffic passes through Burp in plaintext, where it can be logged in HTTP history, modified in Repeater, or fuzzed in Intruder, before being re-encrypted and forwarded. This is the classic structure of a man-in-the-middle: two separate encrypted hops with a readable point in the middle, rather than one continuous encrypted tunnel from browser to server.

The reason this does not simply fail with a certificate warning is trust, not cryptography being bypassed. Browsers validate certificates against a list of trusted root Certificate Authorities; a certificate signed by an authority the browser does not trust triggers a warning or a hard block. Burp's CA certificate is self-generated and, by default, trusted by nobody. Installing Burp's CA certificate into the embedded browser's trust store, and separately into the external browser's trust store for this engagement, is what makes the browser accept Burp's on-the-fly, per-host certificates without complaint. This is precisely why HTTPS interception is only legitimate with explicit authorization and on systems where installing that trust relationship is consented to: the entire technique rests on deliberately weakening the browser's trust anchor for the duration of the test, and reversing that (removing the CA) restores normal certificate validation immediately afterward.

## 3. Reconnaissance picture

Organic navigation of the portal, captured in HTTP history, surfaced a small set of core flows: an unauthenticated login page, a post-login dashboard listing pending submissions, a submission detail/review view, an account settings page, and an administrative user-management area visible only to accounts with elevated roles. Each of these generated a distinguishable request pattern, which made the history easy to segment by feature area once scope filtering removed the third-party noise.

Session handling is cookie-based. A single session cookie is set on successful login and sent on every subsequent request; it does not appear to rotate on privilege-relevant actions such as opening the admin area, which is itself worth tracking rather than concluding on at this stage. Alongside the session cookie, several requests from the dashboard and submission views carry a second, smaller cookie-like value that decodes cleanly in Decoder as Base64 into a compact JSON object carrying a role field and a user identifier. That the client is carrying its own role claim, readable and structurally simple enough to invite tampering, is the kind of detail this phase exists to flag, not to act on.

Parameter behavior is a second thread worth documenting. The submission detail view is reached via a numeric id parameter, and sequential IDs observed during normal browsing suggest the identifier space is small and predictable; no attempt was made to enumerate other IDs during this phase, but the pattern was noted for the access-control hypothesis below. Several search and filter fields on the dashboard reflect their input back into the rendered page's context without an obviously distinct encoding step, visible by comparing a request with a plain value against Burp's rendered response in the browser tab; this was observed, not tested, and no payloads were sent.

Response headers across the application were compared using a handful of requests pulled into Comparer. The comparison showed the portal is missing a Content-Security-Policy header on every response checked, and several endpoints omit X-Frame-Options as well, while Strict-Transport-Security is present but scoped with a short max-age. Error handling was also observed opportunistically: a malformed request to the submission endpoint, sent by lightly editing a captured request in Repeater and resending it, returned a verbose stack trace including internal file paths and the framework version, rather than a generic error page. Finally, the login flow was timed informally by eye across a handful of attempts with valid and invalid usernames; response timing and message wording appeared to differ slightly between "unknown user" and "wrong password" cases, which is flagged below as a hypothesis rather than a conclusion, since no controlled, repeated measurement was performed yet.

## 4. OWASP hypothesis journal (behavior -> 2025 category -> how to test)

This journal records what was observed as testable hypotheses only. Nothing below has been exploited, and nothing here should be read as a confirmed finding; each entry states what would need to happen in the exploitation phase to prove or disprove it.

**Observation: the role/user-identifier value is carried client-side in a decodable, editable cookie, and the admin area's access does not visibly depend on anything beyond that value and the session cookie.**
OWASP category: Broken Access Control.
Why it matters: if the server trusts the client-supplied role claim, or trusts it more than it should relative to a server-side authorization check, a low-privilege account could reach admin functionality by editing that value.
How to test: with an authorized low-privilege account, capture a request to the admin area in Repeater, modify the decoded role field to an elevated value, re-encode it, and observe whether the server grants access or content differs from the baseline low-privilege response, changing only that one value between requests.

**Observation: the submission id parameter is small, sequential, and reachable purely by URL manipulation from the detail view, with no visible ownership check surfaced during normal browsing.**
OWASP category: Broken Access Control (insecure direct object reference pattern).
Why it matters: if the server does not verify that the requesting user owns or is authorized to view the referenced submission, sequential IDs make it trivial to enumerate other users' records.
How to test: from an authorized low-privilege account, request adjacent id values one at a time in Repeater, keeping every other parameter identical to the baseline, and compare whether records belonging to other accounts are returned.

**Observation: Content-Security-Policy is absent on every response checked, X-Frame-Options is missing on several endpoints, and Strict-Transport-Security uses a short max-age.**
OWASP category: Security Misconfiguration.
Why it matters: missing headers do not themselves grant access, but they remove defense-in-depth layers that would otherwise reduce the impact of an XSS or clickjacking issue found elsewhere in the application.
How to test: re-check header presence across a representative sample of endpoints including error pages and static assets, and confirm this is a consistent application-wide gap rather than a one-off on a single route, before recommending remediation.

**Observation: search/filter input on the dashboard appears to be reflected into the page without an obviously distinct encoding step.**
OWASP category: Injection (specifically reflected content that could enable Cross-Site Scripting).
Why it matters: unencoded reflection of user input is the precondition for reflected XSS, which could be used to hijack a staff session given the non-rotating session cookie noted above.
How to test: in the exploitation phase, submit a small set of inert, clearly-marked canary strings (not active payloads) through the filter field one change at a time, and inspect the raw response in Repeater to determine whether special characters are encoded, stripped, or passed through unmodified.

**Observation: a malformed request to the submission endpoint returned a stack trace with internal file paths and framework version information instead of a generic error.**
OWASP category: Security Misconfiguration (with a secondary read as Vulnerable and Outdated Components, pending version confirmation).
Why it matters: verbose error output hands an attacker internal path structure and a specific framework version, which narrows the search for known vulnerabilities considerably.
How to test: reproduce the malformed request deliberately in Repeater, confirm the behavior is repeatable rather than a one-off fluke, and cross-reference the disclosed framework version against public advisories to see whether it maps to known issues.

**Observation: login responses appeared to differ slightly in timing and wording between an unknown username and a known username with a wrong password.**
OWASP category: Identification and Authentication Failures.
Why it matters: a distinguishable response between "no such user" and "wrong password" enables username enumeration, which narrows the target list for credential attacks against real accounts.
How to test: using a small, throttled Intruder run against a short list of known-valid and known-invalid usernames with a fixed dummy password, hold every other input constant and compare response length, wording, and timing across the two categories under repeatable conditions.

**Observation: the session cookie did not visibly change when the account moved from a standard view into the more privileged admin area.**
OWASP category: Identification and Authentication Failures (secondary link to Broken Access Control above).
Why it matters: a session identifier that does not rotate on privilege-relevant transitions increases the value of a stolen session token and can be a sign that privilege is being checked by a claim rather than re-established at the session layer.
How to test: capture the session cookie value before and after navigating into the admin area on an authorized elevated account, and confirm byte-for-byte whether it is identical across that transition.

## 5. Reusable Burp methodology

The workflow below is the distilled version of how this reconnaissance was run, kept as a checklist for the exploitation projects that follow.

Start every session by re-confirming Target scope before touching anything else; scope is set once, at the start, and rechecked any time a new host appears in history, not assumed to still be correct from a previous engagement. Browse the application organically first, through the embedded browser or an external browser routed through the same listener, and let HTTP history populate passively before reaching for any active tool. This organic pass is where most of the reconnaissance picture in Section 3 came from, and it is deliberately slower and quieter than crawling.

Repeater is the default tool for anything that needs a single, controlled, human-paced change: testing one parameter value, re-sending a request with one header edited, or confirming whether a behavior is repeatable. The rule that governs Repeater use throughout this methodology is one change at a time against a known baseline: capture the original response first, change exactly one thing, and compare, so that any difference in the result can be attributed with confidence. Manipulations are kept reversible, meaning the original request is always still available to resend unmodified, and Repeater tabs are labeled and kept, not deleted, so the history of what was tried stays auditable.

Intruder is reserved for cases that genuinely need many variations of the same request, such as the username-enumeration timing check above, and it is used narrowly rather than as a default. On the Community edition of Burp, Intruder is throttled, so any Intruder run is scoped to a short, specific payload list rather than a broad sweep, and is planned around that throttle rather than run blind and left to crawl for an unpredictable amount of time. Where a check would require many more requests than Intruder's throttle comfortably allows, or needs logic beyond simple payload substitution, a small Python script using the requests library is written instead, so that rate, headers, and session handling can be controlled precisely and the results can be logged programmatically for the report.

Decoder is used any time a value looks encoded but its structure is unclear, as with the role/user-identifier cookie in Section 3: decode first, read the resulting structure, and only then decide whether it is worth tracking as a hypothesis. Comparer is used whenever two responses need to be judged as meaningfully different or not, such as the header sweep above or a before/after check in the exploitation phase; eyeballing two long responses side by side is unreliable, and Comparer's diff view removes that guesswork. Inspector, inside Repeater and Proxy, is used to quickly check headers, cookies, and body structure without leaving the request/response pane, and is the first place to look before reaching for Decoder or Comparer on a request that has not been examined yet.

Across all of this, scope discipline and clean history are treated as part of the method, not as bookkeeping on the side. Only in-scope hosts are ever touched, every Repeater and Intruder run stays traceable back to the observation that motivated it, and nothing in this phase was pushed to the point of confirmed exploitation; that boundary is what keeps the hypothesis journal in Section 4 honest and is what the next phase is for.

## 6. Limits

This reconnaissance phase did not cover several parts of the application and several categories of risk, and those gaps should be treated as open, not as an implicit "clean" result. No area of the portal outside the authenticated staff-facing flows and the directly reachable API endpoints was examined; any adjacent subdomains or services noticed in passing were left untouched because they fell outside the authorized host list. Within the in-scope application, only the account role(s) actually available for this phase were exercised; behavior for other role tiers, and the boundaries between them, remain untested beyond the single hypothesis recorded above.

None of the seven hypotheses in Section 4 have been proven or disproven. Every one of them is a plausible reading of an observed behavior, not a confirmed vulnerability, and each still needs the specific, controlled test described next to it before it can be reported as a finding. In particular, nothing was actually submitted to the reflected-input field beyond passive observation, no role value was actually edited and replayed, and no submission ID outside the account's own records was actually requested; those are precisely the actions reserved for the exploitation projects.

Tooling limits also shaped what this phase could see. Community Burp's Intruder throttle meant no broad, exhaustive enumeration was attempted anywhere, including on the submission ID space, so the "small and sequential" observation in Section 3 is based on a handful of organically observed values, not a mapped range. Passive crawling means the Site map is almost certainly incomplete relative to the application's full surface; features gated behind flows that were not exercised during normal browsing (bulk actions, certain admin sub-pages, any export or integration endpoints) were not discovered and are not represented anywhere in this report. Finally, and by design, no denial-of-service style testing, no credential-stuffing scale attacks, and no destructive or state-changing actions were performed at any point; this was a look-and-record phase, and the decision to stop short of exploitation was deliberate, in keeping with the authorization for this stage of the engagement.
